# S072 — verify a wait-to-followup loop on the original project

A completed `waiting` response is an immutable historical reply: replaying its original request returns the original wait and does not observe new evidence. This slice tests whether the existing Project/Controller interfaces can instead capture that wait, explicitly cite it in the action proposal, run the originally preregistered primary, and make a new conditional decision without replacing the Project or its budget. The original plan remains unchanged after registration; changing it would invalidate the original feedback binding. This is a manually authored, model-free engineering flow, not evidence of model adoption or a new scientific finding.

Three persistent synthetic fixtures and an independent fresh-fixture regression were used:

- `project-600c95c060284d0492789db4602eef61`: unknown wait → original waiting case captured/imported to the same Project → exact case ID/version/bundle SHA in the original primary selection proposal → original registration yielded known value `0.0`, satisfying its pre-registered `gte 0` condition → a new conditional request completed audit/freeze/final/report. All 3/3 synthetic tools were used; model/fit 0.
- `project-a8b1612b509b41999c38e17333f01853`: primary used 1/1 tool and original `gte 0` condition was met, but audit candidate was unavailable; native policy returned waiting, with no additional audit/final/freeze. Direct freeze was rejected. An initial driver incorrectly expected `BUDGET_EXHAUSTED`; the traceback and original state were retained.
- `project-dc18b970050c4924ad46ed291c31b44f`: original unstarted condition remained unknown with null value/action/result and 0/3 tools used. Capturing the old waiting snapshot after case import changed the Project was rejected rather than backdating state.

The original waiting, primary and later conditional bodies were replayed in a separate process. Each manager tree and Project state/budget stayed identical: 16/8/7 files, respectively. Full manager-tree hashing and the synthetic normal final/report read synthetic private holdout/report bytes; no process isolation or no-private-I/O claim is made. The standalone regression builds new synthetic inputs without using those persistent fixtures or any historical research project. Its first run put inputs under the Project directory, triggering `UNSAFE_PATH` before any Project action; the failure is retained and the fixed run uses a separate source directory.
