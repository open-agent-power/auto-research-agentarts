# WorkBuddy 分工与阶段交付

## 目标与取舍

第一优先交付是一份基于真实数据、能改变下一步并可接续的研究结果。建议先选 G5 的消费监管条款检索，在同一语料和问题上比较 BM25 与 TF-IDF，考察召回提升是否伴随首个正确匹配排名下降。真实失败、负结果和有效等待均须交付。已有产品入口、预算记录和报告直接复用。重构、界面改版、S139 表格修复和扩充 Agent 均需有选中路径的实际依赖证据。

| 角色 | 要交的结果 | 工作安排 |
| --- | --- | --- |
| 负责人 | 确定课题、范围和状态，给出审批卡，合并验证过的变更，控预算与持有 lease | 责任固定，可兼任来源核验、资料整理或实现 |
| 研究执行者 | 冻结输入、可重跑转换、原生接口适配、真实使用回执、失败与不利样本 | 默认一名，每个文件一名 writer，复用原生实验与持久化 |
| 独立评审 | 数据权利与标注核对、两臂指标独立复算、另一进程接续、签署结论边界 | 不参与同一实现或标签编写，可在输入审核后复用作末期评审 |

常态总共 2–3 人，优先复用原有成员。来源权利查询和源码适配可并行只读，写入由单一 owner 和责任人协调。只分发任务所需的文档、数据范围和产出路径，禁止递归招募。模型档位由 WorkBuddy 已有能力和预算决定。没有独立评审能力时先交付已通过的部分，验收保留 `needs_review`。

## 分阶段执行

| 阶段 | 要做的工作 | 交付与验收 |
| --- | --- | --- |
| **M0 · 课题预注册** | 在干净代码基线上确认原生路径，核候选源字节、权利、转换和标签，设计同 ID 接续并确认冻结与公开边界。可用确定性小样检查输入合同与状态接口。 | GitHub 提交来源清单、协议、审批卡、最小适配和独审意见。每一项来源可复查，两臂使用同一语料和查询，明确竞争解释与停止条件。可私下访问的证据给出 SHA 与位置。实际研究行动为零。 |
| **M1 · 一次真实检索闭环** | 只在新切片获批后，按冻结协议走 ResearchProject、Controller、Workbench，从验证对照取得反馈，按规则等待或执行保存审计，并保存计划差异。 | 有实际原生 Action/Observation/Evidence、两臂验证端点、因反馈选定的下一计划、预算、负例和停机原因。另一参与者能以原 request/body 做只读核对和原入口恢复。验证命中任一分支都可收口。 |
| **M2 · 独立迁移与 CPU 算法** | 只在 M1 已固定结果和局限后，先看结果决定实验。若是否采用新规则仍未知，选择独立检索输入及等预算的有区分反事实。算法线先读 G5-L 原生调度对照和 S014 负结果，选择有结果差异的单一原生候选。 | 两条线各自登记。检索迁移交同预算、独立输入、逐题收益和损失，缺臂记 `unknown`。算法交真实来源或诚实标注的生成负载、独立正确性检查、运行时间和小任务回退记录。两种方法共用项目与证据生命周期，各自持有方法语义。新增真实研究前冻结新范围与额度并取得批准。 |
| **M3 · 产品化与发布判断** | 用干净环境执行复现和交付检查，判断是否有必要做 G2 代理组合、G3 记忆迁移或 G4 候选晋级验证。 | 复现步骤与运行收据、来源与许可证、需求覆盖、失败与限制。G2 要有同任务等预算的可测对照，G3 要有独立任务的效果或负结果，G4 完整门仍需冻结评价与隔离证据，G6 要有独立复现。 |

M0 建议首个会话控制在 60 分钟，来源、标签、适配卡住时在期限内记录缺件及已完成版本。优先用清单与局部回归确认关键接口，有实际阻塞再改一个最小层。若标签审查来不及，交已核部分及剩余具体工作。源提取脚本及协议应当独立重跑，审批卡必须引用实际协议提交和 SHA。M0 阶段内可连续做不依赖研究批准的子项。

M1 暂拟最多 2 个产品研究工具行动，0 产品模型、API、研究 fit、附加原生 evidence 配额。先检查累计数及预留。独审从原榜单和标签复算，不驱动排名、不再次派发。WorkBuddy 平台自身的用量与产品研究用量分别记录，平台若无可见 Token 或成本则记 `unknown`。禁止采购、新付费 API、外发消息、复用已有耗尽的预算或补跑一个新 ID。主代理可在边界内压缩查询与上下文，但冻结后更改协议需重新预注册及审批，不能依据成绩筛题。

## 证明和恢复

- **科学验证**记录比较方向、指标差值、逐题胜平负、至少两项有代表性的遗漏或恶化实例、竞争解释和样本外边界。结果回执绑定实际代码和输入。计划版本须明确哪条观察触发哪个后续方法。
- **工程验证**记录相关测试的运行命令、实际通过或失败；原生路径须验证一个新进程以同 request ID 和相同正文重开已存结果，确认调用和预算无新增。原请求 `pending`、`unknown` 或来源漂移时，只从原实体对账，不能从副本重派发。
- **交付证据**保存源码 SHA、输入/协议/评价器 SHA、项目/run、state 版本或 snapshot、计划和 Action ID、原请求摘要、预算已用/预留、原报告和失败位置。GitHub 只放计划、可发布代码、审核过的汇总与清单。私有证据持久保存并记录访问条件、校验或缺失。源、评价器和旧账本保持原版本。
- **研究成熟度**逐项标记来源验证、主流程运行、决策闭环、独立复核、真实收益是否成立。M1 一例可证明注册规则在该案例实际参与选择。完整 G1 仍要检查至少两轮研究推进、反馈后有依据的变化和他人接续。G5 同时要求两类不同任务的同工作台执行和可复算性。没有同预算反事实时，策略收益与跨任务迁移记 `unknown`。[原阶段门](../../execution/pack-v2/06-roadmap/PHASE_DELIVERABLES_AND_GATES.md)

每个阶段回传北京时间起止、交付路径与精确提交、实测和不利结果、执行者及独审状态、预算、下一判断。团队有可交付工作时继续，只有具体的权限、授权、来源或执行限制挡住依赖项时暂停该项。按阶段回传，不安排新的长驻任务或定时触发。实际执行轮按 [AUTONOMY](../../execution/AUTONOMY.md) 写持久交接。
