## 一句话结论

**不建议的那条修法是错的**：`(id, kept_as)` 在这个包上仍有 **10 处碰撞**——
被保留的文档与被丢弃的副本，`kept_as` 都是 `distractor`。真正能做键的只有
「重打 id」或「加分区字段」；两者都要重建 manifest/ledger，属于新包，不是编辑。

## 五条实测事实

脚本：`scripts/audit_packet_keys.py`（纯标准库 + ElementTree，不导入 `src.autoresearch`，
7 项复算）。产物 `runs/m1b-key-audit-20261119/audit.json`，SHA `4bde36ae…`。

**1. 从源 XML 独立重算，两颗数字都对，但说的不是一件事**

源 `CFR-2025-title16-vol1.xml`（4,422,809 B，SHA `fbaf04e9…b3a9`，与登记值一致）：
992 个 `SECTION`，992 个可解析 `SECTNO`。

| 口径 | 数量 | 说明 |
| --- | --- | --- |
| 编号字符串**完全重复** | **10** | `310.2 310.6 425.1 801.1 803.2 803.5 803.8 803.9 803.10 803.12` |
| 编号**干**冲突（忽略字母后缀） | **15** | 上面 10 个 + 5 对后缀变体 |
| 其中后缀对 | 5 | `3.31/3.31A`、`3.38/3.38A`、`300.20/300.20a`、`300.25/300.25a`、`301.48/301.48a` |

所以最初记的「10 个重复号」与核对轮改成的「15 个」**都不是抄错**：
前者数完全相同的号码，后者把字母后缀变体也算进同一干。对 id 碰撞起作用的是 **10**，
因为 `3.31` 与 `3.31A` 是不同字符串、派生出的 id 也不同，不冲突。

**2. 根因是 id 规则，不是数据**

`id == "d-16-" + sectno`，940 篇 + 52 条排除记录**逐行成立**（0 例外）。
规则里没有副本序号，于是所有同号章节必然折到同一个 id。5 对后缀之所以平安，
只是因为它们的 `sectno` 字符串本身不同——属于运气，不是设计。

**3. `(id, kept_as)` 不成立（本轮主要负结果）**

| 候选键 | 碰撞数 |
| --- | --- |
| `id` | 10 |
| `(id, kept_as)` ← 勘误建议 | **10（不解决）** |
| `(id, 分区)` | 0 |

10 个共享 id 上，`id / part / sectno / kept_as` 四个结构字段**两侧完全相同**；
只有 `subject` 在 1 个 id（`d-16-425.1`）上不同，而 `subject` 是内容不是键，
用它做键等于拿正文识别正文。

**4. 影响面：现在是潜伏的，不是无害的**

「凡 id 在排除清单里就跳过」这种消费方会**误删 10 篇保留文档**。
今天没出事，只因为这 10 个 id 全在 11 个正例 Part 之外：与 qrels 32 篇交集 0、
与 85 篇正例池交集 0。标签没错、计数对账没错（940+52=992），**键错了**。

**5. 两条真能用的修法（都需新包）**

- 给被弃副本重打 id：`d-16-310.2#1` / `#2`，7 项检查已验证 0 碰撞。
- 或加显式 `partition ∈ {corpus, excluded}` 字段，并把 `kept_as` 的取值域与分区解耦。
- 二者都要动 `manifest.json` 与台账 → 违反冻结，只能在新包做；本包**一个字都不改**。

## 门禁补上了那个洞

`scripts/m1b_preflight.py` 新增 **G10「排除清单不得覆盖任何需要的文档」**，
补的正是勘误里列的未做项（原 G8 只查「语料内 id 唯一」，所以 10 处跨清单复用是绿的）。

G10 查四条硬约束：qrels 文档 ⊆ 语料、正例池 ⊆ 语料、正例池 ∩ 排除清单 = ∅、
跨清单共享 id ⊆ 已登记集合。第 4 条用**显式 allowlist**（10 个 id）承担：

> 这条复用是**已登记的缺陷**，包不能改，所以放行；出现第 11 个未登记的共享 id 就 FAIL。

因此 G10 = PASS **不等于**「键没问题」，只等于「共享集合与已登记的一致」。这一点写进了
检查的 detail 字段，免得以后被读成绿灯通行证。

**实测**

- 故障注入自检 **10/10**（原 7 项 + 3 项新增：删掉共享 id 后转 PASS、注入第 11 个共享 id 转 FAIL、
  把带标签文档塞进排除清单转 FAIL）。原有 7 项全部保持通过，说明新检查没破坏旧判定。
- 完整门禁在**包副本**上重跑：`G1–G10` 全 PASS，`verdict GO (10/10)`。
  与 16:57 那次 `GO (9/9)` 一致——**新检查不会追溯推翻已发布的包**，这正是要的效果。
