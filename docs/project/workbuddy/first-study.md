# 首个真实检索课题草案

**研究问题**。给定英文消费者保护场景，系统能否从固定历史条文包找到事前核验的条款。原生 TF-IDF 能否在 BM25 的基础上提高 Recall@20，同时保持 MRR@10。两臂面对相同的原文和查询。更宽的词项匹配可能提高覆盖，文档长度、词形差异或相邻条款也可能使首次命中靠后。结果只说明该历史版条文定位任务的表现。

**状态**。已预检源文件和数据结构。待 WorkBuddy 完成来源权利审查、问题与标签、转换、独审和审批。当前文件是预注册草案。此时没有已登记项目、排名、行动或清算结果。

## 标注与冻结

1. 先按同场景或同条文的相近题分组，固定不同题组的 8 道 dev、24 道 validation。由执行者根据公开真实条文编写场景和核验位置。每题预先写出意图、可接受条号、证据定位和其他容易混淆的条款。使用独立 `q-` ID，保留排除记录。两个分区保留多个 Part 的场景。
2. 独立评审不看排序结果，逐题核对预期条文是否回答问题、是否有未登记的明确共同正例、是否抄标题或暴露条号。无可辨析的改写、重复题组跨集、互相冲突的标签和证据出处不明都须在登记前解决。报告分歧数和处置。若不能得到 32 道合格题，提交缺口并停止，不降低标准去满足数量。
3. 遵循二值正例定义。记录每题正例和未判断范围，不把 qrels 当整部法规的穷尽标注。问题是为实验构造的，验证集在流程上冻结并与 dev 分开。素材为公开历史文本，同宿主可见，人工或代理先前接触状态若不可核记 `unknown`。
4. M0 无真实排名。预检可从干净 Git 基线用结构检查和局部合成合同测试验证调用，不使用真实 validation 结果调整阈值。锁定源码 commit、环境、输入、切分、条款来源映射、预算和失败恢复规则后，单独申请批准。未经批准保持 `prepared_for_approval`。

## 固定方法与决策

- **对照**。BM25，`k1=1.2`、`b=0.75`。**候选**。原生 `tfidf_cosine`。共有 `ascii_alnum_lower_v1`、相同 corpus/query/qrels，按 doc ID 处理平局。比较为候选减基线，使用原生 Recall@20 和 MRR@10 个案及宏平均。nDCG@10、胜平负和两臂共同漏检描述性保留。源、排名器或分区不得随结果更换。
- **事前登记**。验证 `recall@20 > 0` 且 `mrr@10 >= 0`，两个阈值作用于保存的候选减基线差值。阈值是此次小样的实用决策规则，报告原始数值，不把通过解释成统计显著。先注册初始 plan、双指标条件、原预定 primary request 和下表分支。
- **原生顺序**。复用 `LocalWorkbench.register_staged_hypothesis`、`advance_staged_primary`、`advance_staged_feedback`、`save_staged_feedback_plan` 及对应原 body/ID 恢复。在 M0 以实际远端源码确认创建和目的声明、方法注册、报告及恢复入口的兼容性。工程改动只处理实测阻塞。首轮没有终评资产，结论止于 validation。终评和独立迁移由 M2 事前固定兼容路径。[原生入口](../../../src/autoresearch/local_workbench.py) · [原有分支与恢复证据](../../execution/SPRINT-130.md) · [计划保存证据](../../execution/SPRINT-131.md)

| 观察结果 | 事前登记的行动 | 计划与结论 |
| --- | --- | --- |
| 条件全过 | `wait`，无第二工具派发 | 保存由两项原差值支持的等待，方案列入独立复核候选。该语料有支持信号。完整迁移仍待证明。 |
| 至少一项未过 | 同一族 `research.relevance-validation-saved-audit`，只读已有结果，不重新排名 | 定位恶化、漏检和可能竞争解释。保存主结果、审计、具体失败及未来要验证的最小改动。BM25 继续作比较基线。 |
| 未知、未完成或身份漂移 | 保存原请求与回执，以原 ID 核对或等待 | 公开报告标 `unknown`，说明缺件。只在原记录支持时走原入口恢复。 |

独审核原生登记早于 primary，按所有保存排名逐题重算两指标，用原值复算分支。记录主结果、审计或等待和 plan v2 的 SHA/身份。另一个进程使用相同原请求正文恢复，用预算、调用计数及回执验证没有再次派发。若只提供汇总而取不到私有原件，独立复算标 `unknown`。保存原始失败及可定位的恶化例。报告使用“真实源条文定位验证”“按预注册规则作出下一决定”等具体结论，避免从小样推断科研自治、真实用户收益或独立迁移。

## 审批卡要填的字段

- 课题和唯一批准范围，协议和源码 commit，候选原件 SHA，转换、qrels、分区及评价器 SHA，审查证据与运行路径。
- 研究授权建议为 1 个新课题、1 次对照 primary、最多 1 次条件保存审计。总研究工具上限 2。产品模型、API、研究 fit、额外 evidence 配额均为 0。WorkBuddy 自身实际用量按平台可见数据另记。
- 通过和失败边界、原 Project/run/request 的留档位置、已用与预留政策、独立接续位置、公开结果清单。新课题按本次明确获批范围登记，既有请求和预算仍由各自账本维护。
- M0 独审决定为 `ready` 或 `needs_revision` 并逐项给证据。经用户批准才首次调度。下一阶段需要新决定时附一张回答即可推进的审批卡。
