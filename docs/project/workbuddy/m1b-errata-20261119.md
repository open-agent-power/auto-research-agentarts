## E1 · 重复条款号：不是「两个都排除」，是各留一份（计数有两个口径，见 E6）

抽取报告写「10 个条款号各出现两次……两个都排除」。**两处都错。**

卷内实际有 **15** 个条款号各出现两次（口径见 E6：**完全重复 10 个，编号干冲突 15 个**；对 id 碰撞起作用的是 10），处理方式分两类：

- **5 对用字母后缀保留两份**：如 `3.31` / `3.31A`，是两个不同的文档，都进语料。
- **10 个号只留一份，另一份在排除清单里复用同一个 id**：
  `d-16-310.2`、`d-16-310.6`、`d-16-425.1`、`d-16-801.1`、`d-16-803.2`、`d-16-803.5`、
  `d-16-803.8`、`d-16-803.9`、`d-16-803.10`、`d-16-803.12`（其中 9 条记为 duplicate，`425.1` 记为超长）。

后果：

- 影响面：**标签不受影响**。10 个 id 全在 11 个正例 Part 之外（Part 310 / 425 / 801 / 803），
  不进 qrels，也不进 85 篇正例池。
- 但**文档 id 在整个包里不是唯一键**。真正危险的不是连接错配，而是「凡 id 出现在排除清单就跳过」这种
  消费方会**误删一篇保留文档**。语料内部 id 唯一、总数对账正确，**数据没错，键错了**。
- 下一版冻结须把键改成 `(id, kept_as)`，或给被丢弃的那份重打 id。本轮不改——改了就要动 manifest 与 ledger，
  而它们是冻结记录的一部分。**⚠ 第一条已被 [E6](#e6--id-kept_as-证否2026-11-19-补) 实测证否，只有「重打 id」或「加分区字段」可用。**
- 门禁 G8 只查了「语料内 id 唯一」，没查「语料与排除清单不交叉」，所以它是绿的。这是门禁的漏检。
  （已于第 5 轮补为 G10，见 E6。）

## E3 · 「992 条条款」不等于 992 个条款号

52 条排除的构成：**27** 篇 [Reserved]/无正文 + **15** 篇第三方标记 + **9** 篇重复 + **1** 篇超长。

其中 27 篇 [Reserved] 里有 **15 条是区间条款**，例如 § 1.102–1.109、§ 6.171–6.999、
§ 502.200–502.299——一条 `SECTION` 元素代表一整段号段。所以：

- 「本卷 992 个 SECTION 元素」是事实；
- 「992 条条款」不是。940 篇是**文档（SECTION 元素）计数**，不是条款号计数。
- 与 M0 无关：11 个正例 Part 内没有区间条款，85 篇仍是逐条条款。

## E4 · 结果文件的 SHA 记的是 LF 形式，盘上是 CRLF

`ledger.json` 原记 `primary_result_sha256 = 2e351209…`，而文件自身字节的 SHA 是
`42f4c8ac973f09229d0083cdf947af78c44dbf40b684de48cdf46afbed9695ab`。

原因不是文件被改写（mtime 仍是 16:58:18，与执行时刻一致），是 Windows 文本模式写入把 `\n` 扩成了 `\r\n`，
而哈希算的是扩之前的内存字符串。账本现已同时记录 `primary_result_sha256_on_disk` 并写明差异；
`scripts/run_m1b_primary.py` 改为写字节、并对**盘上字节**求哈希，后续包不会再出现这个分叉。

这是本项目第二次栽在行尾上（第一次是 M0 冻结哈希绑定本机行尾）。

## E6 · `(id, kept_as)` 证否（2026-11-19 补）

E1 建议的复合键**不成立**。第 5 轮用 `scripts/audit_packet_keys.py`（纯标准库、不导入
`src.autoresearch`，7 项复算）实测：

| 候选键 | 碰撞数 |
| --- | --- |
| `id` | 10 |
| `(id, kept_as)` ← E1 建议 | **10（不解决）** |
| `(id, 分区)` | 0 |

原因：10 个共享 id 上，被保留的文档与被丢弃的副本 `kept_as` **都是 `distractor`**，
`id / part / sectno / kept_as` 四个结构字段两侧完全相同。只有 `subject` 在 1 个 id
（`d-16-425.1`）上不同，而 `subject` 是内容、不是键。

**同时校正 E1 的计数口径**：从源 XML 独立重算（4,422,809 B / SHA `fbaf04e9…b3a9` / 992 个
`SECTION`），编号字符串**完全重复 10 个**，编号**干**冲突 **15 个**——多出的 5 个是字母后缀变体
（`3.31/3.31A`、`3.38/3.38A`、`300.20/300.20a`、`300.25/300.25a`、`301.48/301.48a`）。
它们 `sectno` 字符串不同、派生 id 也不同，**不参与 id 碰撞**。所以最初记的「10」与 E1 改成的
「15」各自都对着一个口径，但 E1 把两者混成了一句话。对键缺陷起作用的是 **10**，与 10 个共享 id 一一对应。

根因也定位了：`id == "d-16-" + sectno`，940 篇 + 52 条排除记录逐行成立、0 例外——
规则里没有副本序号，同号章节必然折叠。5 对后缀之所以平安，只因其字符串本身不同，属运气。

**可用的修法只有两条，且都要新包**：给被弃副本重打 id（`…#1` / `…#2`，已验证 0 碰撞），
或加显式 `partition` 字段并把 `kept_as` 的取值域与分区解耦。两者都要动 manifest 与 ledger。

E1 第 4 条列的「门禁 G8 未覆盖跨清单交叉」已补：`scripts/m1b_preflight.py` 新增 **G10**，
四条硬约束（qrels ⊆ 语料、正例池 ⊆ 语料、正例池 ∩ 排除 = ∅、跨清单共享 id ⊆ 已登记集合），
故障注入自检 **10/10**，完整门禁在包副本上重跑仍 `GO (10/10)`——新检查不追溯推翻已发布的包。
**注意 G10 的 PASS 只表示「共享集合与已登记的一致」，不表示键没问题。**
